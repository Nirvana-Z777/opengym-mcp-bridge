## Text catalogue integrity

Default source: official v1.4.2 `e9a303877d02e4237b183f96a9a6603990e8fafb`; three source URLs are formed with the full immutable commit, not a moving tag/branch. Source digests are small integrity fingerprints, not bundled exercise data. Runtime import writes format 3 with `source_version`, `source_commit`, `source_files`, `source_digests`, count and translated count. The pinned source has 5,632 rows/Chinese names. Existing format-2 and names-only catalogues remain readable without fabricated provenance.

All three files are mandatory. Failed requests, malformed data, duplicate IDs, invalid overlay references/weights, missing Chinese names or digest mismatch fail before any existing file is replaced. A well-formed but partial JSON response also fails its digest. Unit tests inject synthetic digests only for synthetic fetch fixtures; the CLI has no digest/source override and always uses the published pins. No images, animations, videos or photo bytes are requested.

The fixed source corrects effective-load metadata for these 15 rowing IDs: `0167, 0193, 0208, 0236, 0239, 0571, 0588, 1313, 1318, 1320, 1321, 1323, 1324, 1350, 3200`. Explicit `chest: 0` and `triceps: 0` survive import. The original primary/secondary lists may still mention a zero-weight muscle: membership is not positive training load.

## Additive statistics contract

Existing fields are retained: `primary_sets`, `secondary_sets`, `primary_volume_by_weight_basis`, workout/working-row totals, `volume_by_weight_basis`, `unmapped_sets` and week-to-week changes. These old primary/secondary fields remain descriptive unweighted credits. For compatibility they keep the v0.4.0 role/snapshot behavior; consumers should use the new `effective_sets` when reporting effective muscle load.

Each muscle bucket adds `effective_sets = completed working rows × selected muscle weight`. A unilateral row with at least one completed limb counts once, as in v0.4.0; volume uses the actual completed limbs. Warmups and entirely unchecked rows contribute neither working/effective sets nor work volume. Timed completed work contributes sets with zero load×reps volume. No extra side multiplier, cross-unit/basis conversion or bodyweight load is invented.

Weight source order:

1. A valid explicit `entry.muscleSnapshot.muscleWeights` map.
2. Explicit historical entry weights (`entry.exercise` when present, otherwise direct entry metadata).
3. Current account-custom metadata before official catalogue metadata; explicit weights before canonical defaults.
4. Historical snapshot/entry defaults only when no current mapping is available; otherwise `unmapped`.

An explicit map is authoritative as a whole: absent muscles are not filled from defaults, and an all-zero valid map contributes no effective load. Valid historical maps contain recognized muscle keys with finite numeric values in [0,1]. Unknown keys are ignored; invalid known weights invalidate that map and trigger fallback. Numeric strings/null/booleans are not treated as explicit historical weights. With no explicit map, canonical primary muscles get 1.0 and supporting muscles 0.4; aliases, groups and body-part-only fallbacks follow the reviewed official contract. Per-week `muscle_weight_sources` counts working rows attributed to each selected source, `effective_unmapped_sets` distinguishes missing mapping from intentional zeros, and top-level `muscle_weight_catalogue` reports available version/commit provenance.

| Example: two completed work rows | Legacy descriptive fields | New effective load |
| --- | --- | --- |
| Corrected row, no historical weights | Any chest/triceps membership may still receive descriptive credits | Upper back 2.0; biceps 0.8; chest/triceps 0 |
| Old snapshot has explicit chest 1.0, triceps 0.4 | Existing snapshot roles retained | Chest 2.0, triceps 0.8: the recorded historical weights deliberately win |
| Snapshot has chest 0 and no other weights | Existing credits retained | Chest 0; no catalogue weights filled in |

Every calculation is read-only: no training rows, exercise IDs or snapshots are rewritten. A catalogue refresh can change the effective interpretation of records without weight snapshots, which is why provenance and source accounting accompany the result. Existing explicit historical positive chest/triceps weights are not silently "corrected".

## Remaining limits and release advice

- Real browser rendering, PWA cache/background behavior and Android/iOS/Watch hardware remain untested. happy-dom sync modules are not a substitute for device testing.
- Photos are synthetic references and clear markers only; no image upload, download, byte retention or OS health synchronization was tested/added.
- Core API/conditional-write compatibility is confirmed for the two exact official pins. This does not certify future upstream releases, huge profiles, ARM or NAS/network-filesystem behavior.
- Old local catalogues need a separately authorized refresh for the v1.4.2 corrected weights. No production refresh or history migration is included; retain the single-Bridge/account recommendation.
- Code is ready for review once final CI passes. The original device-test limitations still apply to a later release decision. **Do not merge, tag v0.4.1, create a Release, publish GHCR or upgrade production under this task.**
