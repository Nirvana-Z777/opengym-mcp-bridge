# v0.4.0 feature and safety reference

v0.4.0 develops directly from v0.3.2 (`d3de870b4f98439ed6701c127ffe23bf7c8bcf70`), skipping v0.3.3. The owner approved GitHub merging, tagging and image publication on 2026-10-21 after isolated acceptance. Package/lockfile versions and release image examples are **0.4.0**. NAS upgrades remain a separately authorized operation.

## Integrated changes

All original 19 MCP tools remain available with their existing inputs. The writable configuration now exposes 37 tools; the read-only configuration exposes 22. `OPENGYM_ALLOW_WRITES=0` hides and domain-gates both local mutations and formal upstream writers. Private reads remain protected by the existing MCP bearer authentication; stdio assumes a trusted local process.

### Existing routine editing

`preview_plan_change.actions` additionally accepts:

| Type | Required fields beyond type |
| --- | --- |
| `rename_routine` | `routine_id`, `name` |
| `add_routine_exercise` | `routine_id`, `exercise: {exercise_id, sets, reps, weight?}`, optional zero-based `index` |
| `remove_routine_exercise` | `routine_id`, `exercise_index` |
| `replace_routine_exercise` | `routine_id`, `exercise_index`, `exercise` |
| `move_routine_exercise` | `routine_id`, `exercise_index`, `to_index` |

Keep using `set_exercise_target` for sets/reps/weight goals. Indices refer to the result of earlier actions in the same proposal. IDs, scheduling and unrelated state are preserved. Empty routines, duplicate IDs, unknown exercises, invalid indices and replacing a different exercise when unsupported extension fields could be lost are rejected. Same-ID replacements preserve extensions.

Use `apply_plan_change` only after human approval of the whole preview. The existing GuardedWrites boundary still requires enabled writes, exact confirmation `我确认写入`, an unexpired proposal, fresh revision/write ID/content check, mandatory preimage backup, one CAS PUT and verification by rereading. Nothing retries on timeout or conflict.

### Durable workout drafts

1. `start_workout_draft {date, name, routine_id?, note?}` creates an empty draft using supplied actual information. Optional `routine_id` is the exact existing ID returned by `get_plan`, not an A/B/C display name. No planned sets are copied as measured results.
2. `draft_add_exercise {draft_id, expected_revision, exercise_id, weight_basis?, note?}` appends a known official/custom exercise. `weight_basis` is `as_recorded` (default), `per_dumbbell` or `pair_total`.
3. `draft_add_set {draft_id, expected_revision, exercise_index, set}` appends one actual set. The set contract is the same as `preview_workout_log`, including timed rows, warmup/work phase, RIR/RPE and measured asymmetric `sides.L/R`. Ordinary and unilateral rows cannot be mixed in one per-dumbbell occurrence.
4. `draft_update_set` additionally takes `set_index` and replaces the entire set. `draft_remove_set`, `draft_remove_exercise` and `draft_set_note` correct the draft. Every mutation uses the latest `expected_revision` and returns a new revision.
5. `list_workout_drafts {limit?, offset?}` returns paginated summaries; `get_workout_draft {draft_id}` resumes the complete saved draft. Each result includes its status/revision.
6. `preview_finish_workout_draft {draft_id}` passes the full draft through the original completed-workout validator and statistics recalculation. The response includes the complete formal workout preview, draft revision, upstream revision and 10-minute proposal. Every remaining occurrence needs a completed set. Dates/weights/reps are never invented. Unknown session times/durations remain unknown; this version does not infer them from draft timestamps.
7. After the human approves the entire preview, `commit_finished_workout_draft {proposal_id, confirmation: "我确认写入"}` submits the completed session once through the existing backup/CAS/verify flow. Separate proposal kinds prevent `log_workout` from bypassing the durable journal. Edits after preview invalidate the draft revision; a second proposal cannot commit the same draft.
8. `abandon_workout_draft {draft_id, expected_revision}` cancels only an OPEN draft. It retains a private audit record and makes no upstream change.

Just before the network boundary, after successful backup/version checks, a durable journal stores the intended stable workout ID, exact workout content and source revision, and changes the draft to `verification_pending`. The journal is fsynced before PUT. Crash, timeout, 409/refusal, mismatching reread or failed local settlement cannot silently reopen the draft. Definite rejections conservatively remain pending for manual investigation as well.

`recover_workout_draft {draft_id}` reads upstream after restart or an uncertain result. It can mark the LOCAL journal committed only when exactly one non-deleted/non-undone workout with the stable ID and full expected content exists at a newer revision (allowing the same server bookkeeping fields as the original verifier). It issues **no upstream PUT**. Missing, duplicate or changed records remain locked. Never recreate/retry such a workout automatically. Human investigation of the account and private backup is required if exact recovery is impossible; there is no force-unlock tool.

### Account-private storage

Runtime storage is a `local/` sibling of `cfg.catalogueFile`, normally `/store/local/<account-scope>/drafts/` and `/store/local/<account-scope>/feedback/`. The existing `/store` mount persists it across container recreation. Scope is SHA-256 of the upstream base URL and the stable official `/api/me` user ID, not a token/name. Re-pairing to another account/base URL isolates old private records. A missing stable ID fails closed. Never change pairing files while the Bridge is running; restart after an intentional re-pair.

Files use UUID names, schema version, revision, 0600 mode, 256 KiB bound, exclusive temporary files, fsync, atomic rename and directory fsync. Direct/ancestor symlinks and symlink records are refused. Directories use 0700 mode. Local mkdir locks coordinate competing store instances and protect revision updates. There are at most 50 open drafts and 10,000 documents per directory. Lists/results are paginated or bounded to 128 KiB; narrow excessive queries. Storage is private through filesystem permissions, **not encrypted**.

Use a single Bridge container per paired account. These filesystem locks are not a distributed transaction across multiple Bridge processes or network filesystems; GuardedWrites itself is process-local and upstream CAS remains authoritative. A process crash while holding a lock leaves it in place to fail closed. During separately authorized maintenance, stop all Bridge instances, inspect the journal/upstream/backup and remove only a verified stale lock. There is no automatic expiry or takeover. Do not blindly remove locks or copy pending drafts to new IDs. Preserve `/store/local` together with existing backups before future production upgrades. Downgrading to v0.3.2 leaves these files intact but cannot display them.

### History/progress analysis

`get_workout_progress {exercise_id, from?, to?, limit?, offset?}` returns measured set details for each separate occurrence, completed work-set counts, reconstructed volume, best load and assistance meaning. Totals are split by weight basis. Pagination offsets are not frozen snapshots: restart pagination if history changes.

`get_weekly_training_summary {from, to}` uses explicit inclusive local calendar dates, Monday weeks, at most 366 days and includes empty weeks. It reports workouts, completed working rows, volume split by weight basis, primary/secondary muscle set credits, primary volume, unmapped sets and changes from the previous displayed week. Boundary weeks can be partial. One unilateral row counts as one set; volume sums actual completed limbs. Warmups/unchecked rows are excluded. Timed rows add sets and zero load×reps volume. Muscle snapshots with actual primary IDs take precedence; otherwise current catalogue metadata is used. Each primary gets full credit; secondary sets remain separate, so muscle totals overlap. Missing metadata is not guessed. Drops/rest-pause semantics reuse existing v0.3.2 calculations; unsupported layouts fail explicitly.

Numbers are descriptive reconstruction, not estimated muscle stimulus or verified physiological load. Bodyweight resistance is never inferred; assistance load is not bodyweight minus assistance. No history weights are converted. Unit follows the current account setting because historical unit changes cannot safely be reconstructed. Do not compare incompatible bases or units as if they were one precise progression series.

### Body weight and feedback

`record_body_feedback {date, body_weight?, unit?, feedback?}` stores supplied body weight (explicit `kg` or `lb` required) and/or feedback in Bridge-private storage. `list_body_feedback {from?, to?, limit?, offset?}` reads these records. Records explicitly return `source: bridge_private` and `synced_to_opengym: false`. No health facts are inferred.

The official state has native bodyweight history (still readable through `get_summary`). This PR deliberately implements private capture for both bodyweight and feedback; it does not claim these records appear in the official app and does not invent upstream feedback fields or assume native weight-sync semantics from raw JSON shape. Native bodyweight synchronization would need a separately reviewed preview/commit adapter and upstream merge/stamp evidence. No direct unsupported upstream schema mutation is included.

## PR #3 review follow-up — 2026-10-21

### Exact A/B/C routine association

A draft can retain the existing A, B or C plan's exact `routine_id` from `get_plan`. The ID is validated against the paired account's current routines, including native deletion stamps. The association persists on disk and appears in draft detail/list results. Finishing carries it through the original workout validator into official `routineId` and `routineIds`; the full preview shows `routine_id`, `routine_ids` and the current `routine_name`. Saved-workout detail also exposes these IDs. Names are display text, never identity; renaming a routine does not change the link. No production plan IDs or exercise prescriptions are embedded in code/tests.

`draft_set_routine {draft_id, expected_revision, routine_id}` associates or changes the plan of an OPEN draft; `routine_id: null` explicitly unlinks it. This supports drafts saved before the association feature without discarding their measured sets. It is a local write, gated by enabled writes and revision checking. Changing the association advances the draft revision, so a previously approved finish preview cannot submit the changed link. Pending/committed/abandoned drafts cannot be relinked. Omitting the field on an existing or new freestyle draft continues to mean no link, even if its name matches an A/B/C plan.

Routine availability is revalidated during finish preview. A removed routine blocks finishing rather than silently detaching the session. Any upstream change after preview still triggers the unchanged GuardedWrites revision/content conflict check. A pending submission journal retains its exact intended routine IDs for restart verification; recovery never guesses a replacement plan.

### Deletion and Undo statistics compatibility

The two v0.4.0 read-only analytics now respect the reviewed v1.4.1 native deletion contract in [`sync-merge.js`](https://github.com/DuarteSantos8/openGym/blob/v1.4.1/frontend/src/lib/sync-merge.js): `state.deleted.workouts` is a map keyed by stable workout ID (or the native legacy `date|start` key). Positive deletion timestamps suppress an older/equal stored record; a later record edit remains available. A negative add-back timestamp represents Undo and permits the restored record that is actually present in `workouts`. A tombstone never recreates an absent session. Unstamped records use the native end/start-time fallback. Root `undone` and per-field `_u` metadata do not mean that all training data should be discarded.

Regression scenarios cover physical removal, a still-present stale row with a positive deletion stamp, equal timestamps, newer edits, negative Undo stamps, repeat delete/Undo cycles, legacy keys and missing timestamps, empty history, and missing rows despite add-back markers. They verify actual progress records, working volume, muscle credits, empty weeks and week-to-week differences. Cached `vol`, PR badges and held weights do not reintroduce deleted sessions into these analytics. Pending-draft recovery also refuses a matching but currently tombstoned workout, and can settle it after an exact restored record is visible. No deletion, undo, restore or statistics-repair writer is added.

Full local regression after this follow-up: **155 passed, 0 failed, 0 skipped** (131 prior tests plus 24 association/deletion/Undo cases). All fixtures remain synthetic; no real A/B/C plans or production history were read. Confirmation, proposal expiry, backup, CAS, one PUT, durable journal and reread verification remain in force. Formal release and NAS acceptance remain separately authorized.
