# v0.5.1 开发与验收

v0.5.1 从正式版 v0.5.0 的提交 `7e6f97e09e1080d46fc0dccc6f675c3a3136b9c2` 开发。本次修复目录刷新和账户写入预览之间的竞争。当前发布镜像仍为 `ghcr.io/nirvana-z777/opengym-mcp-bridge:0.5.0`。

## 预览失效与并发

每个账户写入预览在读取数据前捕获当前目录代次。注册提案时比较代次，提交时在锁内重新检查。成功替换目录后，Bridge 在释放锁前推进代次并清除已有账户提案。正在计算的旧代次预览会收到 `expired`。已返回的旧提案在创建账户备份和发出 PUT 之前被拒绝。

动作目录刷新与账户写入共用每个 Bridge 进程的一把锁。账户写入持锁覆盖修订号、write ID 和内容检查，备份、单次 PUT 以及回读。刷新持锁覆盖候选文件下载及校验、比对现有文件摘要、备份与原子替换。重叠操作收到 `busy`。同一目录的刷新另有文件锁，检测正在使用的目录或上次留下的锁。

刷新前后都校对绑定到预览的目录摘要，最终检查发生在原子替换前。下载失败、固定 SHA-256 或官方 JSON 结构不符、磁盘目录冲突、备份和替换失败都会阻止覆盖。失败或无变更不会推进代次。目录更新只修改 Bridge 的本地官方目录副本。草稿完成所需的本地草稿修订号和提交元数据与账户提案共存，受同一代次保护。历史显式肌群快照仍优先用于 `effective_sets`。

## 运维与限制

刷新使用 `get_catalogue_status`、`preview_catalogue_refresh`、`apply_catalogue_refresh`。需由用户确认所见的完整预览，然后用新目录重新预览待执行的账户变更。[备份、目录恢复、NAS 升级和回滚](operations.md)

每个本地存储运行一个 Bridge 写入进程。目录锁可检测其他刷新进程，但进程内的提案和账户写入协调不跨 Bridge 实例。CLI 导入和手动恢复都应先停止 Bridge。重启会丢弃内存提案，已保存草稿保持持久化。若目录备份成功后替换失败，备份可能保留供诊断。若替换成功但锁清理失败，刷新仍推进代次并返回清理提示。

正式部署前，备份现有配置与私有存储，记录现有镜像摘要。待正式发布后再选定镜像并只重建 Bridge。回滚 Bridge 镜像会保留本地存储和已经由 openGym 接受的写入。目录回滚是独立的单文件恢复操作。
